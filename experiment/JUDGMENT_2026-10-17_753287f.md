## A. E2 — accepted; one re-labelling upstream: the WikiSQL FULL protocol gives the number of conditions

Checked in the code: `v11_wikisql.py` line 192 scores FULL as `all(argmax(COND_k ⊗ COL) == c for k, (c, o, v) in enumerate(conds[:4]))` — it
iterates over the GOLD conditions, so (i) the number of conditions is given, and (ii) a decoded condition beyond the gold count is never
penalised (the slot argmax always returns a column; "absent" is never asked). `v12_wikisql_baselines.py` line 128 zips the same way, so the
transformer and bag-of-words rows are on the same protocol: the comparison between models is fair and stands as it is. What does not stand
is the label. Corrections, all wording, no number moves:
1. RESULTS 8c and 8d, and the WikiSQL row of STATUS: "FULL query (selected column + aggregator + every condition column; the NUMBER of

   FULL query (the number text-to-SQL papers compare)" is wrong and is struck: logical-form accuracy in the WikiSQL literature requires the
   operators, the values and the number of conditions; our FULL is a column-structure number under a given count, comparable only across
   our own same-protocol models.

## C. Question 0 — the set-size reading: NOT now; PLANNED with its criterion

Decision: leave it. Three reasons.
1. Nothing in the article depends on it. The article's WikiSQL claim is on the count-given protocol, the same for every model, now
   labelled; the product readout is reported as it is and reads as a limit. A fix built in a hurry before submission would be one more
   number to defend; the limit stated is the better paper.
2. It is a mechanism of the tool, not a choice of P1's legend. Whatever legend the team's data brings, any set-valued role needs a size
   reading, and WikiSQL's sizes (1–4, mostly 1) may not be P1's. It belongs to the tool's next round, built once P1's data says which
   set-valued roles exist and how large they are.
3. The rules: one change per run, criterion before the run, evaluation before data before optimisation before architecture.
Written as PLANNED, with this criterion: WikiSQL dev, 3 seeds — decided set exact ≥ 0.55 (the count-given reading re-measured on the same
3 seeds beside it; 0.628 on seed 0), FULL decided ≥ 0.38 (8c's count-given number), the false-size rate on the 0-condition questions
printed. Two candidate single changes, in this order: (a) a RELATIVE member rule on the stored membership scores — a column is a member if
its score ≥ β · the question's best score, β fitted on calibration rows by the round-6 rule; a re-scoring of the saved models, no
retraining, CPU; (b) a count role in the legend (closed values 0–4), one retraining. (a) first, by the order of the rule. If the session
wants one cheap thing before stopping, (a) is permitted (saved seed-0 model, CPU, minutes); it is not required, and it does not enter the
paper either way.

## G. Can the tool and the server demonstrate something on natural text now? Yes, within stated bounds

What exists and is measured: the path export → legend → train → formalize → check → diff ran on 64,776 real questions; the server returns
a frame with per-role margins, presence margins, `_unplaced`, `_empty`, `_depth`, and the verifier's verdict; the legend-gap report proposes
lines with the N6 statistics; abstention is on the wire. WikiSQL IS a natural-text demonstration: the queried column at 0.82 from the
question alone, 0.05 confident-wrong on it at τ = 0.05, and the package abstaining on 52% of the questions and saying so — shown as a
feature, not hidden. A demo built on the server today is credible in a domain that fits the tool's bounds: a legend of a few roles; gold
frames from structured data (SQL, forms, API calls, logs) or from a few hundred model-annotated sentences audited by hand; a lexicon of
kinds from the corpus (skip-gram clusters, as on WikiSQL); single-event sentences at depth 0–1 (device commands, database questions, ticket
or form fields). What it cannot do yet, and any demo must say: values (numbers, dates) are invisible to the reader; one event per sentence,
`if` / `must` / `may` / `and` not decoded by the tool's decoder; mood by a heuristic; the size of a set-valued role (C); unknown words get
the kind `unknown` (no tagger); presence across new formulations overlaps by ~10%; the annotator step has never run (no key); multi-world
dispatch strategy 3 not built; no coreference, no discourse. So: a demonstration on open text — chat logs, articles — is not credible now
and should not be attempted; a demonstration on domain commands or questions is, if the domain is chosen by the bounds above, the legend is
written before the data is touched, and abstention is part of what is shown. The cheapest credible demo is WikiSQL itself behind the
server (already measured); the first real one is P1's domain after the article, and its first requirement is the annotator key and the
audited gold set, not more mechanism.
